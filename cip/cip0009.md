# CIP-0009: Make GP and GPLVM working-state caches explicit

## Status

- [x] Proposed
- [ ] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Replace the pattern of large `mutable` working matrices updated inside `const` methods on `CGp` and `CGplvm` with an explicit cache/invalidation protocol (or non-`const` update paths) so factorisations and gradients cannot silently go stale and the models are safer to reason about.

## Motivation

`CGp` and `CGplvm` keep most intermediate state (`Am`, `Lm`, `invK`, Cholesky factors, gradient workspaces, and similar) in `mutable` members. `const` methods recompute and write those caches. That design made sense when the API wanted logical constness for likelihood evaluation, but it has three costs:

1. **Reasoning** — readers cannot tell from the signature whether a call mutates cached factors.
2. **Threading** — concurrent likelihood or gradient calls on one model are unsafe by construction.
3. **Staleness** — a missed `KupToDate`-style flag after a parameter or data change is a correctness bug that `checkGradients` only catches when someone runs it.

The post-CIP-0007 review ranked this after [CIP-0008](cip0008.md) (matrix ownership). It supports **Assert Invariants and Verify Against Reference** without changing the mathematical models.

## Detailed Description

### Current state

- Dozens of `mutable CMatrix` (and related) fields in `CGp.h` and `CGplvm.h`.
- Flags such as `KupToDate` gate some recomputation; coverage of every write path is unclear.
- Public APIs expose `const` log-likelihood / gradient entry points that fill the caches.

### Approach

Work in layers; stop when the models are auditable even if some `mutable` remains behind a narrow interface.

1. **Inventory** — List every `mutable` field and every method that writes it. Map setters of parameters, `X`, `y`, and kernel/noise to invalidation points.
2. **Protocol** — Introduce a small explicit API, for example:
   - `invalidateCache()` / `ensureKUpToDate()` (names TBD) called from all mutating setters;
   - or a nested `Cache` object held by value, updated only through non-`const` methods, with `const` likelihood taking a snapshot or requiring a prior `update()`.
3. **Migrate** — Move the hottest paths (`updateK`, `updateAD`, gradient assembly) onto the protocol. Prefer removing `mutable` from fields that no longer need it over renaming in place.
4. **Verify** — Existing matio / GP tests; add a focused test that changes a parameter and asserts recomputation (for example via a counter or by checking that a stale Cholesky would fail a known identity).
5. **Concurrency** — Document that a single model instance remains single-threaded unless a later CIP adds locking. Do not claim thread safety from this CIP alone.

### Non-goals

- Multi-threaded training in this CIP.
- Rewriting sparse approximations (DTC/FITC/PITC) algorithms.
- Kernel ownership modernization ([CIP-000A](cip000A.md)), though both touch large headers and should not land in the same PR.

## Implementation Plan

1. Complete the mutable-field / invalidation inventory in this CIP (appendix or linked note).
2. Agree the protocol shape (flag helpers vs nested cache object).
3. Implement for `CGp`, then `CGplvm`, with Reference tests green after each.
4. Document the protocol in `docs/` and compress when closed.

## Testing Strategy

- Full matio Reference suite.
- Gradient checks on GP / GPLVM paths already covered by tests or demos.
- New regression for invalidation after a parameter write.
