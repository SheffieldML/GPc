# CIP-0013: Performance — GPy-referenced benchmark harness and kernel/BLAS improvements

## Status

- [x] Accepted - Approved, ready to start work

## Summary

Implement [REQ-0007](../requirements/req0007_competitive-default-build.md): a correctness-gated benchmark against an independent reference, and the kernel and default-build changes that benchmark is there to test.

A like-for-like comparison with GPy 1.15, on two-dimensional spherical RBF with one BLAS thread, gives:

- **Full GPs:** GPc with OpenBLAS is up to 26% faster than GPy at \(N \ge 1000\).
- **Sparse models:** GPc is 1.5–2× slower for variational DTC and 2.5–3× slower for FITC.
- **BLAS library, same flags:** with reference BLAS, GPc is 3–9× slower than with OpenBLAS. Both sides of that ratio were built with `g++ -O2 -DNDEBUG`. Shipped `make.linux` is a further, unmeasured step down: `-ggdb -DDBG`, no optimisation level, `-llapack -lblas`.

Profiling attributes the sparse gap to kernel evaluation. Distances, `exp`, and bounds checks are 55–60% of a sparse evaluation. Level-2/3 BLAS is the same order of magnitude as GPy.

This CIP delivers:

1. A benchmark harness in the repo, gated on likelihood agreement.
2. A ranked set of changes, each re-measured on that harness:
   - P1. Link OpenBLAS by default, and add `make RELEASE=1`.
   - P2. A `GPC_CHECKS` switch on the existing bounds macros.
   - P3. A cheap `dist2Row` for small input dimension.
   - P4. A thin `CStationaryKern` (GPy `Stationary`-shaped) owning bulk distances and matrix-level `compute` / gradient shells; RBF first via `K_of_r`-style hooks; compound kernels dispatch to children.
   - P5. One per-evaluation workspace on that base, replacing the half-used per-class `updateX` / `Xdists` caches.

**Close this CIP** when the harness is in-repo and P1–P5 meet REQ-0007 on the q=2 protocol: full GP does not regress, and VarDTC/FITC are at most 1.3× GPy. The projected 1.0–1.2× after a bulk kernel is a hypothesis, not the gate.

**Leave to other CIPs.** The whitened sparse path, and a later 1.1× re-benchmark, belong to [CIP-0012](cip0012.md). A threading study (P7) is optional and does not block closure.

REQ-0001 and REQ-0002 are already validated. They record that the tools build and that the reference suite runs. They are prerequisites. They are not the requirements this CIP implements.

## Motivation: benchmark findings (2026-11-15)

### Protocol

- **Models:** RBF + Gaussian noise, 2-D inputs on \([-3,3]^2\), \(y = \sum_q \sin x_q + \varepsilon\), \(\sigma_n^2 = 0.01\), lengthscale 1, variance 1.
- **Inducing inputs:** a random subset of \(X\), identical in both packages and optimised in both (\(Mq\) extra gradient entries).
- **Model mapping:**

| | GPy | GPc |
|---|---|---|
| Full GP | `GPRegression` | `FTC`, with kernel `rbf + white(0.01)` |
| Variational DTC | `SparseGPRegression` (VarDTC) | `DTCVAR`, β = 100 |
| FITC | `SparseGP` + `FITC()` | `FITC`, β = 100 |

- **Correctness gate before timing.** Both log-likelihoods were checked against an independent dense NumPy calculation at the same parameters:
  - GPc matches to ~1e-5 for the full GP and DTCVAR.
  - FITC differs by exactly \(\tfrac N2\log 2\pi\): the double count recorded in CIP-0012 F5.
  - GPy differs by ≤ 0.4 nats on the sparse models, consistent with its jitter on \(K_{uu}\).
  - Parameter counts match: 3 for the full GP; \(2Mq+3\) for the sparse models.
- **Metric:** median wall time of one objective plus gradient evaluation (`_objective_grads` in GPy; `setOptParams` + `computeObjectiveVal` + `computeObjectiveGradParams` in GPc). Parameters are perturbed between repeats to defeat caches, with 2 warm-up runs and 3–20 timed repeats.
- **Environment:**
  - Shared: 2-core x86-64 (Cooper Lake), one BLAS thread on both sides (`OPENBLAS_NUM_THREADS=1`).
  - GPy: 1.15.0 on NumPy 2.5.3 / scipy-openblas 0.3.34.
  - GPc: g++ `-O2 -DNDEBUG`, linked against either OpenBLAS 0.3.26 (Ubuntu `openblas-pthread`) or reference BLAS/LAPACK 3.12.

### What these numbers do and do not show

- **The 3–9× ratio is the BLAS library at fixed flags.** Every GPc column above was compiled `-O2 -DNDEBUG`. It is not a measurement of shipped `make.linux`, which is `-ggdb -DDBG` with no `-O` and `-llapack -lblas` (`make.linux` lines 8 and 49). `-DDBG` exposes private methods in `CGp.h`. It does not add numeric checks. P1 therefore has two effects: the measured library gap, and an unmeasured `-O0` versus `-O2` gap. The harness measures the second before this CIP quotes a combined factor for the default build.
- **The ranking is for \(q = 2\).** Level-1 BLAS call overhead dominates a distance at two columns. On the oil data that overhead is a smaller share, and P4's matrix distance matters more than P3's entry loop. The harness records \(q\). A q=2 speedup is not a claim about higher input dimension.
- **Linear algebra is the same order of magnitude, not a matched profile.** On VarDTC 10k/200, level-2/3 BLAS is 28% of GPc's 440 ms (`perf` self-time), about 120 ms. GPy's cProfile self-time is led by `dtrtrs` at 46% of 245 ms. The two profilers do not account time the same way. The supported conclusion is that both linear-algebra shares sit around 100–150 ms, while GPc's kernel share is about 270 ms against GPy's about 85 ms.
- **1.0–1.2× after a bulk kernel is a hypothesis.** The close gate is REQ-0007: at most 1.3× GPy for VarDTC and FITC after P1–P5.

### Does GPy's distance caching skew the comparison? No.

GPy's `Stationary._scaled_dist` is `@Cache_this(limit=3)`, so the concern is that GPy reuses distances across evaluations. Instrumenting `_unscaled_dist` and varying which parameter is perturbed shows otherwise:

| Model | Perturb first param | rbf.variance | lengthscale | all params | `_unscaled_dist` calls / eval |
|---|---|---|---|---|---|
| Full GP, N=2000 | 453 ms | 459 | 448 | 460 | 1.0 |
| VarDTC 10k/200 | 246 | 243 | 259 | 232 | 3.0 |
| FITC 10k/200 | 209 | 216 | 209 | 211 | 3.0 |

- Any parameter change invalidates the cache, because the kernel itself is an observed argument. Distances are recomputed every evaluation.
- What GPy saves is reuse within an evaluation. Each distance block (\(K_{ff}\) for the full GP; \(K_{uu}\), \(K_{uf}\) and the diagonal for sparse) is computed once and shared between \(K\), `update_gradients_full` and `gradients_X`.
- That within-evaluation reuse is what GPc lacks, so it belongs in the comparison.
- Distances cost GPy only 10–14% of its time, against 17–27% for GPc at \(q = 2\).

### Where the time goes

**GPy** (cProfile, 6 evaluations; inclusive %):

| Model | `_unscaled_dist` | `K_of_r` | `update_gradients_full` | `gradients_X` | Top self-time |
|---|---|---|---|---|---|
| Full GP, N=2000 | 9% | 7% | 22% | – | `dpotri` 25%, `jitchol` 19%, `dtrtri` 18% |
| VarDTC 10k/200 | 10% | 8% | 20% | 16% | `dtrtrs` 46% |
| FITC 10k/200 | 12% | 9% | 24% | 19% | `fitc.inference` 49% |

GPy's sparse path is dominated by triangular solves. That is the whitened formulation CIP-0012 proposes for GPc, and the 1.1× check lives there.

**GPc** (`perf`, self time; Legacy, OpenBLAS, \(q = 2\)):

| Category | Full GP N=2000 | VarDTC 10k/200 | FITC 10k/200 |
|---|---|---|---|
| BLAS/LAPACK level 2/3 | 49% | 28% | 41% |
| Distances (`dist2Row` → 2× `dnrm2` + `ddot` per entry) | 17% | **27%** | 20% |
| `exp` | 12% | 18% | 15% |
| Bounds checks (`ndlCheckBounds` / `ndlCheckDimension`) | 4% | 9% | 8% |
| Scalar kernel gradients (`getGradParams`, `getGradX`) | 3% | 8% | 6% |
| Other | 15% | 11% | 11% |

### Code-level causes

1. **`CMatrix::dist2Row`** computes \(\lVert x\rVert^2 + \lVert y\rVert^2 - 2x^\top y\) with two `dnrm2_` calls (overflow-safe scaling loop, then squared) and a `ddot_`, for every kernel entry. At \(q = 2\) the call overhead dwarfs the arithmetic. A direct loop (the commented "WVB approach") is already in `CMatrix.h`.
2. **The bulk entry points exist and the GP does not call them.** `CKern::compute(K, X)` and `compute(K, X, X2)` walk `computeElement`. `CGp::_updateK` inlines that same walk (comment: "bulk path is a future optimisation"). `CCmpndKern::compute` is commented out in `CKern.cpp`. The benchmark kernel is `rbf + white`, so an override on `CRbfKern::compute` is unreachable until the compound kernel sums its children's `compute` results and `_updateK` calls `pkern->compute`.
3. **`exp` and distances are recomputed in every gradient routine:**
   - `CRbfKern::getGradParams(X, X2, covGrad)` recomputes `dist2Row` and `exp` for every entry.
   - `getGradX` does the same per inducing point.
   - For \(K_{uf}\) each distance and exponential is computed up to 3×.
4. **One cache already exists, and only part of it is read.** `CRbfKern::updateX` stores \(X\)–\(X\) distances and part of \(K\) (`Xdists`). The symmetric gradient path uses it. `_updateK` ignores it. Cross-covariances never use it. P5 replaces this cache. It does not add a second one beside it.
5. **Bounds checks ignore `-DNDEBUG` on the default path.** In `ndlassert.h`, `BOUNDCHECK` and `DIMENSIONMATCH` call `ndlCheckBounds` and `ndlCheckDimension` unless `_NDLCASSERT` is set. With `_NDLCASSERT` they are `assert`, and `NDEBUG` already removes them. The default build does not define `_NDLCASSERT`, so the checks remain inside an optimised binary. P2 switches those existing macros. It does not add a third mechanism. `-DDBG` is unrelated (see above).
6. **Default Linux link is reference BLAS** (`make.linux`: `-llapack -lblas`). `make.osx` already uses OpenBLAS.
7. **Default compile flags are `-ggdb -DDBG`**, with no optimisation level. The table does not include this configuration.

### P1 and P2, as patches to the current macros and flags

- **P1** changes `make.linux` and the Linux CI job. `make.osx` already links OpenBLAS. Every Linux build links OpenBLAS, including a bare `make`. `make RELEASE=1` selects `-O2 -DNDEBUG` and turns `GPC_CHECKS` off, and the README's Linux run instructions use that target. Reference tests and the correctness CI job stay on the checking build. The benchmark artifact is built with `RELEASE=1`.
- Quote two numbers from the harness after P1, separately: OpenBLAS versus reference BLAS at `-O2`, and shipped flags versus `RELEASE=1`. Do not add them into a single "versus the old default" factor until both have been measured.
- **P2** edits `ndlassert.h` only. `GPC_CHECKS` chooses between `ndlCheckBounds` / `ndlCheckDimension` and the `_NDLCASSERT` `assert` path (already removed by `NDEBUG`). `MATRIXPROPERTIES` and `SANITYCHECK` stay on; they are not the inner-loop cost in the profile.

### P3, P4, and P5: one kernel path

P4 overrides the virtuals `CKern` already has. It does not add a second public API next to them. The shared stationary machinery lands in a new intermediate base, not as a copy-paste on `CRbfKern` alone.

- **`CStationaryKern`.** Subclass of `CKern`, mirroring GPy's `Stationary`: one place for unscaled distance, lengthscale scaling, and the bulk `compute` / gradient shells. Concrete isotropic kernels (`CRbfKern`, then Matérn 3/2 and 5/2, rational quadratic, exponential, cosine, and later ARD stationary types) reparent under it and implement only the radial maps—\(K(r)\), \(\partial K/\partial r\), and how those combine into parameter gradients—equivalent to GPy's `K_of_r` / `dK_dr`. Non-stationary kernels (`CLinKern`, white, Brownian, coregionalization) stay direct `CKern` children. The existing `stationary` flag stays consistent with the type.
- **Land RBF first on that base.** The close gate is still `rbf + white` on the q=2 protocol. Other stationary kernels move onto the same distance and workspace path in the same P4/P5 change set where cheap, or immediately after RBF if that keeps the review small; do not ship a second independent bulk implementation per class.
- Restore `CCmpndKern::compute` so it evaluates each child with `compute` and accumulates. White noise stays a diagonal contribution. `_updateK` calls `pkern->compute` for \(K\), \(K_{uu}\), and \(K_{uf}\).
- Keep `computeElement` as the test oracle. Bulk and element-wise \(K\), `getGradParams`, and `getGradX` agree to `MATCHTOL` on random inputs, including near-duplicate points.
- **Numerics.** The GEMM distance cancels when points are close. Clamp \(r^2 \ge 0\) and set the diagonal of a symmetric block to exactly 0, as GPy does. The matio suite remains the arbiter. If a fixture moves past `MATCHTOL`, keep the direct-difference loop for small \(q\).
- **P3** is the small-\(q\) form of the same distance, used by `CStationaryKern` and by any remaining scalar paths. A scalar loop is the right call when \(q\) is 2 because the level-1 call overhead is the cost. P4's `dgemm` is the form that matters once \(q\) or the block is large. P3 does not claim the 17–27% share at oil-data dimension.
- **P5 replaces per-class `updateX` / `Xdists`.** Today RBF, rational quadratic, and both Matérns each keep a private `Xdists` cache; only part of the RBF path reads it. The workspace lives on `CStationaryKern` and holds \(r^2\) and \(K\) for the three blocks of one evaluation. Gradient shells on the base consume those values instead of calling `dist2Row` again. Invalidation is `invalidateCache()` / `ensure*UpToDate` from CIP-0009, so a parameter change forces recomputation, as in the GPy cache experiment. The old `Xdists` members go away in the same change. A workspace that survives from one evaluation to the next is a bug.
- **Not a prerequisite CIP.** Harness and P1–P3 do not wait on `CStationaryKern`. The base is introduced with P4/P5, not as a separate improvement plan before performance work.

### P6 and P7

P6 is implemented and closed under CIP-0012. This CIP's harness is the instrument for CIP-0012's ≤ 1.1× note. Nothing in the checklist below waits on that number.

P7 is a study. Ownership moved to [CIP-0025](./cip0025.md) (GEMM distances + OpenMP). If the numbers are uninteresting it is marked abandoned there; this CIP can still close without P7.

### Benchmark harness

- `bench/benchGPc.cpp`: timing driver. Prints median objective-plus-gradient time, log-likelihood, parameter count, \(q\), BLAS identity, compiler flags, and thread count.
- `bench/run_bench.py` generates the shared data and runs the GPy comparison. It refuses to report a timing unless GPc, GPy, and a dense NumPy log-likelihood agree, allowing the documented FITC \(\tfrac N2\log 2\pi\) constant until CIP-0012 F5 is fixed.
- `make bench` and a non-gating CI job upload `bench.csv` and the ratio table as an artifact. Timings on shared runners are too noisy to gate on. The job builds the harness with `RELEASE=1`. The existing test workflow stays a checking build.
- The `-L` short-flag collision (CIP-0012 F5) does not affect the harness, which uses the C++ API.

## Implementation Plan

1. Land the harness against the current binary, including the shipped-flags row that the 2026-11-15 table lacks. Correctness gate on; timings are artifacts.
2. P1, P2, P3. Re-run the harness after each. Matio suite and `testKern` stay green.
3. P4 and P5 together: add `CStationaryKern`, reparent RBF, restore compound dispatch, keep the element-wise oracle, and delete per-class `updateX` / `Xdists` in the same change. Move the remaining stationary kernels onto the base before closing, or immediately after the RBF gate if the review needs splitting—without a second bulk path.
4. Re-benchmark the q=2 protocol. Close when REQ-0007's 1.3× bar holds. Record \(q\), BLAS, flags, and threads beside the table in `docs/`.
5. P7 only if someone wants the study. CIP-0012 re-uses the harness for its own 1.1× note when that CIP lands.

## Backward Compatibility

- Model streams are unchanged. Kernel type names in streams stay the concrete classes (`rbf`, `matern32`, …); `CStationaryKern` is an internal base only.
- `computeElement` and the element-wise `getGradParams` / `getGradX` remain, and tests still call them.
- Every Linux link line uses OpenBLAS. `make.inc` still overrides `make.linux` for a local BLAS.
- `make RELEASE=1` is the documented build for running models: `-O2 -DNDEBUG`, bounds checks off. A bare `make` may keep `-ggdb` for development, and it still links OpenBLAS. Reference tests and correctness CI keep bounds checks.

## Testing Strategy

- **Correctness:** matio reference suite and `testKern` stay green after each step. P4 adds bulk-versus-element-wise equality tests (≤ `MATCHTOL`) for \(K\), `getGradParams`, and `getGradX` on random inputs, including near-duplicate points, for every kernel reparented under `CStationaryKern`.
- **Composition:** the benchmark model is `rbf + white`. Tests call `compute` on that compound kernel and compare with the sum of element-wise evaluations.
- **Coverage:** CIP-0011's `CGp.cpp` threshold is maintained. New kernel paths are covered in `testKern`.
- **Performance targets** (1 thread, OpenBLAS, q=2 protocol), which are the REQ-0007 bar:
  - Full GP: no regression against the 2026-11-15 OpenBLAS column.
  - VarDTC and FITC: at most 1.3× GPy after P1–P5.
  - Default Linux `RELEASE` build: no worse than that OpenBLAS column.
- **Not a close gate of this CIP:** at most 1.1× GPy after CIP-0012. That check is written into CIP-0012's testing strategy and uses this harness.
- **Recorded with every row:** \(q\), BLAS library, compiler flags, thread count, machine. A second machine is allowed to disagree; the artifact is the comparison.
