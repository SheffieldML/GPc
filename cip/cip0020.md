# CIP-0020: CMake when packaging forces it — keep makefile as blessed native path

> CIPs describe HOW to achieve requirements (WHAT). This CIP extends the contemporary build story from [REQ-0001](../requirements/req0001_contemporary-build.md) / [CIP-0001](./cip0001.md) without reopening that closed CIP. It supports [REQ-000E](../requirements/req000E_gpy-facing-python-facade.md) / [CIP-001D](./cip001D.md) wheel packaging and keeps [REQ-0007](../requirements/req0007_competitive-default-build.md) / [CIP-0013](./cip0013.md) OpenBLAS / `RELEASE=1` semantics intact under any new generator.

## Summary

Introduce CMake as an **on-demand** build path for packaging and portability drivers (Python wheels via scikit-build-core, and later a maintained Windows path), while the **blessed native developer and CI path remains the makefile** (`make.linux` / `make.osx` → `make.inc`). Archive the obsolete root `CMakeLists.txt` immediately so it cannot be mistaken for support. Do **not** dual-maintain full target parity or cut over Compile / Reference / Coverage workflows until CMake reproduces those gates.

**Which requirements?** [REQ-0001](../requirements/req0001_contemporary-build.md) (how we keep building), [REQ-000E](../requirements/req000E_gpy-facing-python-facade.md) (wheel / installable façade), [REQ-0007](../requirements/req0007_competitive-default-build.md) (BLAS and release flags must remain correct under any new generator).

## Motivation

REQ-0001 is already **Validated** on make + OpenBLAS + matio CI. The live question is not “can we compile?” but “when does a second build system earn its keep?”

Drivers that favour CMake:

1. **Python packaging** — CIP-001D Phase A builds `_gpc` with a makefile against `libgp`. Shipping wheels wants scikit-build-core (or equivalent), which expects a CMake (or meson) description of the native bits.
2. **Out-of-tree / install layouts** — `cmake --install` and `find_package`-style consumption are awkward to fake in the 400-line hand-rolled `makefile`.
3. **Windows** — docs defer a Windows CI path until a maintained fragment exists; CMake is the usual way to express MSVC + BLAS without another one-off `make.win`.

Non-drivers (do not justify a full cutover now):

- Modelling, sparse factorisation, or gradient work (CIP-001B and friends).
- “CMake is modern” as aesthetics — the makefile already meets Assert-and-Verify gates.
- Replacing `make.inc` BLAS selection for day-to-day local builds that already work.

The root `CMakeLists.txt` (dated ~2020) pointed at an external `mlprojects` tree, `ndlfortran.c` / f2c, and Eigen paths that **do not match this repository**. Leaving it at the root falsely signalled support and conflicted with Fortran hygiene (blessed build compiles `ndlfortran.f`).

Tenets: **Interoperate With the GP Ecosystem** (wheels, future Windows); **Flexibility Without a Performance Tax** (build system stays outside the SCG loop); **Assert and Verify** (no CI cutover until matio / smoke parity); **LAPACK Owns the Linear Algebra** (FindBLAS/OpenBLAS must preserve CIP-0013 defaults).

## Detailed Description

### Locked decisions (for Proposed review)

1. **Makefile remains blessed** for local `gp` / `ivm` / `gplvm` / `bgplvm`, `matio-tests`, coverage, numerical-stability, and GitHub Actions **until** an explicit later phase proves CMake parity and maintainers accept cutover. README and `docs/build-and-ci.md` continue to document make first.
2. **Trigger, not calendar** — substantive CMake work starts when CIP-001D needs wheels, or when a Windows CI CIP is Accepted — not because the makefile is “old.” (Accepted early so Phase 0–A can land as packaging prep.)
3. **Phase 0 is housekeeping** — move the dead root `CMakeLists.txt` to `make/legacy/CMakeLists.txt.archive-2020` and note in docs that thin CMake is CIP-0020; make remains blessed. Coordinate with the Fortran hygiene backlog item that already mentions stopping references to `ndlfortran.c`.
4. **Thin CMake first** — living `CMakeLists.txt` builds `libgp` (C++17, Fortran `ndlfortran.f`, OpenBLAS/LAPACK, optional matio) and CLI smoke targets (`gp`, optionally `ivm` / `gplvm` / `bgplvm`). It does **not** need every demo/test binary on day one. Shared object list lives in `cmake/GpcSources.cmake`.
5. **Options mirror make semantics** — `GPC_USE_MATIO`, Release vs Debug aligned with `RELEASE=1` / bare make. Do not invent a second BLAS policy.
6. **Python integration** — prefer scikit-build-core invoking the thin CMake for wheels (Phase B); keep `python/Makefile` working against root `libgp` for editable Phase A–C development until wheels replace that path.
7. **No dual-source-of-truth forever** — during transition, CMake uses `cmake/GpcSources.cmake` aligned with makefile `libgp` objects. Long-term either make generates from CMake, or make is retired after cutover — decide at Phase C, not now.
8. **Rejected for this CIP:** meson as primary generator; rewriting the Fortran bundle to remove `gfortran` as a prerequisite; replacing BLAS discovery with a vendored copy; cutting over CI while make and CMake disagree on flags or test sets.

### Effort sketch (order-of-magnitude)

| Phase | Scope | Effort |
| --- | --- | --- |
| 0 | Archive dead CMakeLists; doc note | hours |
| A | Thin CMake: libgp + gp smoke + OpenBLAS + Fortran + optional matio | ~2–4 days |
| B | Extension / scikit-build wheel path consuming Phase A | ~2–5 days (with CIP-001D) |
| C | Full test/demo/bench parity + CI cutover decision | ~1–2 weeks + soak |

### Alternatives considered

- **Makefile-only forever** — fine for native CI; fails when wheel builders and Windows contributors need a standard generator. Deferred only until those drivers exist.
- **Big-bang CMake rewrite** — high regression risk against matio / coverage gates; blocks modelling CIPs. Rejected.
- **Keep dusty CMakeLists as “starting point”** — wrong layout and deps; more expensive to revive than rewrite. Rejected.

## Implementation Plan

1. **Phase 0 — Clear false support**  
   - Archive dead root `CMakeLists.txt` → `make/legacy/CMakeLists.txt.archive-2020`.  
   - Pointer in `docs/build-and-ci.md` / README: CMake is CIP-0020; make is blessed.  
   - Ensure Fortran hygiene does not revive `ndlfortran.c` for CMake.

2. **Phase A — Thin CMake**  
   - New root `CMakeLists.txt` + `cmake/GpcSources.cmake`: `libgp`, Fortran via `enable_language(Fortran)`, FindBLAS/OpenBLAS, C++17.  
   - Options: `GPC_USE_MATIO`, Release vs Debug aligned with `RELEASE=1`.  
   - Targets: `gp` (and optionally `ivm` / `gplvm` / `bgplvm`) for smoke.  
   - Document: `cmake -B build && cmake --build build`.

3. **Phase B — Packaging bridge**  
   - Wire scikit-build-core / `python/pyproject.toml` to the thin CMake.  
   - Preserve editable makefile path until wheel install is documented and tested.  
   - Smoke: import `gpc`, FTC learn on a tiny problem (CIP-001D gates).

4. **Phase C — Parity and cutover**  
   - Add matio-tests / `ctest` equivalents for the hard gate set (`cmake/GpcTests.cmake`, `-DGPC_BUILD_TESTS=ON`).  
   - **Cutover decision (locked):** do **not** switch GitHub Actions Compile / Reference / Coverage to CMake in this CIP. Makefile stays the blessed native CI path. CMake remains packaging-first (Phase B) plus optional maintainer `ctest`. Dual maintenance is acceptable: shared sources live in `cmake/GpcSources.cmake`; makefile object lists stay the CI source of truth until a future CIP revisits cutover.

## Backward Compatibility

- Developers who `cp make.osx make.inc && make gp` keep working through Phases 0–B.  
- No change to `.model` streams, matfiles, or CLI flags.  
- Wheel users may gain a pip-install path; that is additive.  
- Archiving the dead `CMakeLists.txt` is not a user break (it never built this tree).

## Testing Strategy

- **Phase 0**: docs / tree hygiene only; no behaviour change.  
- **Phase A**: `cmake` build of `gp` help smoke on Ubuntu and macOS (local or optional non-gating workflow). Link line must use OpenBLAS (or documented Accelerate) consistent with CIP-0013.  
- **Phase B**: existing CIP-001D pytest / FTC smoke against the wheel or scikit-build editable install.  
- **Phase C**: `ctest` (or scripted) run matching `make run-matio-tests` before any hard CI cutover. Assert-and-Verify: shapes and reference fixtures still gate merges.
