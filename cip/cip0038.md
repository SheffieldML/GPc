# CIP-0038: GPy `kern` inventory on `gpc` — wrap existing, add cheap stationaries

> CIPs describe HOW to achieve requirements (WHAT). This CIP extends the Python façade subset of [REQ-000E](../requirements/req000E_gpy-facing-python-facade.md) so GPy’s common single-output kernels are reachable via GPy-shaped constructors. Paths stay on [CIP-0014](./cip0014.md) / [REQ-0008](../requirements/req0008_gpy-like-parameter-access.md). Phase A surfaces the [REQ-0005](../requirements/req0005_gpy-aligned-kernel-coverage.md) / [CIP-000C](./cip000C.md) catalogue already in C++; Phase B adds small GPy stationaries that GPc still lacks (`Sinc`, `ExpQuadCosine`).

## Summary

Close the gap between GPy’s public `kern` surface and `gpc.kern` in two phases: **(A)** wrap every single-output covariance GPc already implements; **(B)** implement then wrap the cheap missing stationaries GPy added after CIP-000C’s cut (`Sinc`, `ExpQuadCosine`). Document the three naming layers (Python class, path segment, stream type). Explicit inventory below so “missing from the façade” is not confused with “missing from C++” or “out of scope zoo.”

**Which requirements?** Primary: [REQ-000E](../requirements/req000E_gpy-facing-python-facade.md). Exercises [REQ-0005](../requirements/req0005_gpy-aligned-kernel-coverage.md) and [REQ-0008](../requirements/req0008_gpy-like-parameter-access.md). Phase B extends REQ-0005’s catalogue in spirit (new `CKern` types + fixtures).

## Motivation

CIP-000C closed a *slice* of GPy alignment (Matérn ±ARD, RatQuad ±ARD, Exp, StdPeriodic, Cosine, Brownian). CIP-0015 wired those into `gp learn -k`. The Python façade ([CIP-001D](./cip001D.md)) still only exposes six constructors. Separately, GPy itself grew past that slice: e.g. **`Sinc`** and **`ExpQuadCosine`** (SheffieldML/GPy #872) have **no** `C*Kern` in GPc — wrapping cannot invent them. A naïve “wrap CIP-000C” CIP under-counts both the façade gap and the C++ gap.

## Case / naming status (current wraps)

GPy has **three different spellings** for the “same” kernel depending on surface. GPc already mirrors that on the C++ path façade; the Python package only partially exposes it.

| Layer | Role | GPy example | GPc today (exposed wraps) | Status |
|-------|------|-------------|---------------------------|--------|
| **Python class** | Constructor | `GPy.kern.RBF`, `ExpQuad`, `MLP` | `gpc.kern.RBF`, `ExpQuad`, `MLP`, `ArcCosine`, `White`, `Bias` | Match for the six exposed types |
| **Path segment** | `set_by_path` / `param_paths` / display | `rbf.lengthscale`, `ExpQuad.variance`, `mlp.weight_variance` | CIP-0014 `gpyComponentName()` + leaf conversion | Match; leaves snake_case (`lengthscale`, `weight_variance`); ExpQuad is the intentional PascalCase component |
| **Stream / parts `type`** | Factory / serialisation | (GPy has no exact twin) | lowercase GPc types: `rbf`, `eq`, `mlp`, `arccos`, … | Internal; parts lists use these |

**Already correct for current wraps**

- Constructor **PascalCase** matches GPy class names (`RBF` vs path `rbf` is intentional — same as GPy).
- Constructor kwargs are **snake_case** (`lengthscale`, `weight_variance`, `bias_variance`) matching GPy.
- After build, paths go through C++ CIP-0014: `rbf.*`, `ExpQuad.*`, `mlp.*`, `white.*`, `bias.*`, `ArcCosine.*`.
- String `kernel=` aliases accept mixed case for the small set (`RBF`, `ExpQuad`, `MLP`, `ArcCosine`).

**Known quirks (keep; do not “fix”)**

- `RBF` class → path prefix `rbf` (lowercase); `ExpQuad` class → path prefix `ExpQuad` (PascalCase). That is GPy/`paramz`, not a bug ([CIP-0024](./cip0024.md)).
- Parts dict `"type"` stays GPc stream spelling (`eq` not `ExpQuad`); the binding maps type → class and then sets paths with `gpyComponentName()`.
- Legacy camelCase leaf aliases (`weightVariance`, `lengthScale`) remain accepted on C++ paths; `paramPaths()` emits GPy snake_case only.

**Gaps this CIP closes**

- No Python classes for Matérn / RatQuad / Exp / StdPeriodic / Cosine / Brownian / Linear / Poly (and ARD where GPc has separate classes).
- `addPartsCompound` rejects those types even if a hand-built parts list is passed.
- No documented matrix of class ↔ path segment ↔ stream type for the full CIP-000C set on the façade (native docs already have CLI examples with `Mat32.*` / `std_periodic.*`).

## Detailed Description

### GPy `kern` inventory vs GPc (public constructors from `GPy/kern/__init__.py`)

| GPy class | In GPc C++? | This CIP |
|-----------|-------------|----------|
| `RBF`, `ExpQuad`, `White`, `Bias`, `MLP` | Yes | Already on `gpc.kern` (keep) |
| `Add` | `CCmpndKern` | Already `+` / `Add` |
| `Matern32`, `Matern52`, `Exponential`, `RatQuad`, `Cosine`, `StdPeriodic`, `Brownian`, `Linear`, `Poly` | Yes (CIP-000C / older) | **Phase A — wrap** |
| `OU` | Same maths as `Exponential` in GPy | **Phase A — alias** of `Exponential` |
| **`Sinc`** | **No** | **Phase B — implement + wrap** |
| **`ExpQuadCosine`** | **No** | **Phase B — implement + wrap** |
| `ArcCosine` | Yes (CIP-0028; GPy has no twin in `__init__`) | Already on `gpc.kern` |
| `Coregionalize` | Yes | **Phase D —** `Coregionalize` / `IndexWhite` + `util.multioutput.ICM`/`LCM` + `GPCoregionalizedRegression` |
| `Prod` | `CTensorKern` | **Phase C —** `*` / `Prod` → nested `tensor` parts |
| `PeriodicExponential`, `PeriodicMatern32/52` | No (spectral periodics; distinct from `StdPeriodic`) | Out of scope |
| `WienerVelocity`, `Spline`, `TruncLinear*`, `LinearFull`, `Fixed`, `WhiteHeteroscedastic`, `Precomputed`, `GridRBF`, `Symmetric`, basis-func kernels, `DiffKern`, integral / multioutput / IndependentOutputs / Hierarchical | No or partial | Out of scope |
| `ODE_*`, `EQ_ODE*`, `LFM*`, `sde_*`, `DEtime` / `DiffGenomeKern`, `SplitKern` | No | Out of scope (REQ-0005 non-goals) |

GPc-only extras (not GPy `__init__`): `IntegratedBrownian`, `Whitefixed`, `IndexWhite` — optional Phase A stretch for `IntegratedBrownian` only; others stay CLI/stream.

### Phase A — wrap existing C++ into `gpc.kern`

| `gpc.kern` class (GPy name) | Parts / stream `type` | Path segment (`gpyComponentName`) | Constructor kwargs (GPy-natural) |
|----------------------------|------------------------|-----------------------------------|----------------------------------|
| `Matern32` | `matern32` | `Mat32` | `variance`, `lengthscale` |
| `Matern52` | `matern52` | `Mat52` | `variance`, `lengthscale` |
| `Exponential` (`OU` alias) | `exp` | `Exponential` | `variance`, `lengthscale` |
| `RatQuad` | `ratquad` | `RatQuad` | `variance`, `lengthscale`, `power` |
| `StdPeriodic` | `stdperiodic` | `std_periodic` | `variance`, `period`, `lengthscale` |
| `Cosine` | `cosine` | `Cosine` | `variance`, `lengthscale` |
| `Brownian` | `brownian` | `Brownian` | `variance` (enforce `input_dim==1`) |
| `Linear` | `lin` | `linear` | `variance` |
| `Poly` | `poly` | `poly` | `variance`, `weight_variance`, `bias_variance`, `degree` |

Also expose ARD for types that already have `*ard` classes: `Matern32(..., ARD=True)` → `matern32ard`, same for Matérn52, RatQuad, Linear, RBF, MLP, Poly. Path prefixes stay CIP-0014 (no invented `lengthscale_i` unless conversion already exists).

### Phase B — new cheap stationaries (GPy parity maths)

Implement as `CStationaryKern` subclasses with `testKern` fixtures (numpy / GPy twin generator), stream factory, CLI `-k`, CIP-0014 path names, then façade constructors:

| Class | \(K(r)\) (GPy) | Path segment | Notes |
|-------|----------------|--------------|-------|
| `Sinc` | \(\sigma^2\,\mathrm{sinc}(2r)\) with GPy’s `np.sinc` convention | `Sinc` | Gradients need the same small-\(r\) guard as GPy |
| `ExpQuadCosine` | \(\sigma^2\exp(-2\pi^2 r^2)\cos(2\pi r/T)\) | `ExpQuadCosine` | Extra `period` param; spectral-mixture style |

These are small closed forms — same cost class as Cosine — not ODE/LFM. They are **in scope** for this CIP because wrapping alone cannot close the GPy gap users will notice next to Cosine/StdPeriodic.

### Out of scope (still)

- PeriodicExponential / PeriodicMatern\* (different construction from StdPeriodic)
- ODE / LFM / SDE / integral / basis-func / DiffKern / multioutput wrappers
- Private / frozen-W coreg variants (GPy `Private`)
- Changing CIP-0014 ExpQuad/`rbf` dual naming
- Claiming API identity with GPy

### Implementation approach

1. Freeze inventory table against current `GPy/kern/__init__.py` (re-check on accept).
2. **Phase A:** `gpc.kern` descriptors + `addPartsCompound` branches; `setByPath` with GPy path segments (`Mat32.lengthscale`, …).
3. **Phase B:** `CSincKern` / `CExpQuadCosineKern` + fixtures + factory + CLI + paths + façade.
4. **Phase C:** `*` / `Prod` → nested `{"type":"tensor","parts":…}` → `CTensorKern` (White summed outside).
5. **Phase D:** `Coregionalize` / `IndexWhite` / `active_dims`; `gpc.util.multioutput` (`build_XY`, `ICM`, `LCM`); `GPCoregionalizedRegression`.
6. Docs/tests: subset checklist, side-by-side, CIP-002F help list, pytest path round-trips; optional notebook cell (Matérn + StdPeriodic + Sinc).

### Design locks

1. **Compose Through Interfaces** — descriptors only; maths stay in `CKern`.
2. **Ecosystem Interoperability** — class names and path segments follow GPy; stream types stay GPc.
3. **Assert and Verify** — pytest path round-trips; no silent rename of unknown types.
4. **Three-layer naming table** in this CIP (and compressed later into `docs/python-facade.md` / `param-paths.md`) is the source of truth for case.
