# CIP-0043: ReLU covariance with MLP parameterisation

> CIPs describe HOW to achieve requirements (WHAT). This CIP serves [REQ-001A](../requirements/req001A_deep-gaussian-processes.md) (deep GPs with any inducing family per layer) and [REQ-0018](../requirements/req0018_bayesian-gplvm-without-psi-statistics.md), with gates under [REQ-0002](../requirements/req0002_runnable-verification.md) and the weight-space conditioning outcome of [REQ-000D](../requirements/req000D_jitter-free-sparse-conditioning.md).

## Summary

Add a ReLU counterpart of the Williams (1996) MLP covariance. It has the same parameters as `CMlpKern` (`weightVariance`, `biasVariance`, `variance`) and an ARD sibling like `CMlpardKern`. Then make it work everywhere `mlp` / `mlpard` work today: dense GP, sparse and SVGP inducing (points, weight-space ridge, Hermite), deep GP (C++ and Python façade, per layer), SVI Bayesian GP-LVM, GP-LVM, the CLI tools and `gpc.kern`.

The work is mostly plumbing. The kernel itself is closed form, and GPc already has the ReLU building blocks (`arccosSoftReLU`, the order-1 ridge paths of `CArcCosineKern`). The value is in the gradient gates and in removing the `kernel == "mlp"` special cases that currently exclude any other dot-product kernel.

## Motivation

### What exists, and what is missing

`CArcCosineKern` with `order = 1` is already a ReLU kernel (Cho & Saul 1 = \(\tfrac{\sigma^2}{\pi}\|\tilde x\|\|\tilde x'\|J_1(\theta)\)). It is not the ReLU analogue of `CMlpKern`:

| Capability | `CMlpKern` / `CMlpardKern` | `CArcCosineKern` order 1 |
|---|---|---|
| Weight and bias variances | `weightVariance`, `biasVariance`, `variance` | none — fixed \(\Sigma=I\), only `variance` |
| ARD form | `CMlpardKern` | none |
| Batched `inducingGradX` / `inducingGradZ` (CIP-003F) | overridden | not overridden — falls back to the per-datum `getGradX` loop |
| `getGradParam` (single index) | not implemented | not implemented |
| Deep GP (`deepgp.cpp`, `wrap_deepgp.cpp`) | `mlp`, `mlpard` | refused (`makeLayerKern` throws) |
| Python `inducing='weightspace'` / `'hermite'` in `DeepGP` | requires `kernel == "mlp"` | refused |
| Python `SparseGPRegression` / `GPLVM` string kernels | `mlp` | `ArcCosine` for GP only |
| `ppa`, `ivm`, `gplvm` CLIs | `mlp` | none |

So a user who wants a ReLU deep GP with a learned input scale per layer cannot have one. Deep ReLU networks are the standard comparison for deep GPs (Cho & Saul 2009; Dunlop et al. 2018; Dutordoir et al. 2021), and the ReLU kernel is also the one for which the layer-to-layer propagation of \(\|\mathbf x\|\) is exactly homogeneous, which matters for the `mlp_init='scaled'` question in [CIP-0041](./cip0041.md).

### Why not just use `ArcCosine` order 1

Three reasons.

- Fixing \(\Sigma=I\) on \(\tilde x=(x,1)\) hard-codes the input scale. Deep GP layers have no standardised inputs, so the optimiser needs a scale handle (`weightVariance`) and a bias handle (`biasVariance`), as `mlp` gives it.
- `CArcCosineKern` has no ARD form.
- Its inducing-gradient paths are the slow base-class loops.

`CArcCosineKern` stays as the \(\Sigma=I\) reference. This CIP generalises order 1 rather than replacing it, and the Phase 0 gates tie the two together.

## Detailed Description

### Covariance

For weights \(\mathbf w\sim\mathcal N(0,\Sigma)\), \(\Sigma=\operatorname{diag}(\sigma_w^2 I_d,\sigma_b^2)\), and augmented input \(\tilde{\mathbf x}=(\mathbf x,1)\), the infinite-width ReLU network has covariance

\[
k(\mathbf x,\mathbf x')=\mathbb E\big[\max(0,\mathbf w^\top\tilde{\mathbf x})\max(0,\mathbf w^\top\tilde{\mathbf x}')\big]
=\frac{\sigma^2}{2\pi}\,a^{1/2}a'^{1/2}\big(\sin\theta+(\pi-\theta)\cos\theta\big),
\]

with \(a=\sigma_w^2\|\mathbf x\|^2+\sigma_b^2\), \(a'\) likewise, \(\cos\theta=\dfrac{\sigma_w^2\,\mathbf x^\top\mathbf x'+\sigma_b^2}{\sqrt{a\,a'}}\), and \(\sigma^2\) the output variance (`variance`). The diagonal is \(k(\mathbf x,\mathbf x)=\tfrac{\sigma^2}{2}a\).

Compare `CMlpKern`: \(k=\sigma^2\arcsin\dfrac{\sigma_w^2\,\mathbf x^\top\mathbf x'+\sigma_b^2}{\sqrt{(a+1)(a'+1)}}\) (no \(2/\pi\) prefactor; see `CMlpKern::computeElement`). The ReLU kernel has no `+1` in the denominator. The unit-variance output weight that produces it in the erf case is absent here, and ReLU is positively homogeneous: \(k\) scales as \(\|\tilde x\|_\Sigma\|\tilde x'\|_\Sigma\) rather than saturating, so the diagonal grows with \(\|\mathbf x\|^2\). ARD replaces \(\sigma_w^2\|\mathbf x\|^2\) by \(\sum_q\sigma_{w,q}^2x_q^2\) (and the matching inner product).

**Convention.** We match `CArcCosineKern` order 1 when \(\sigma_w=\sigma_b=\sigma=1\), up to the constant \(1/2\) that separates the \(\mathbb E[\max(0,\cdot)\max(0,\cdot)]\) normalisation from Cho & Saul's \(2\mathbb E\) normalisation. The exact relationship is pinned by a unit test (Phase 0), not by this prose.

**Identifiability.** \(k\) is homogeneous of degree one in \((\sigma_w^2,\sigma_b^2,\sigma^2)\) jointly: scaling all three by \(c\) scales \(k\) by \(c\), and scaling \(\sigma_w^2,\sigma_b^2\) by \(c\) while dividing \(\sigma^2\) by \(c\) leaves \(k\) unchanged. So there is a flat direction in \((\sigma_w^2,\sigma_b^2,\sigma^2)\). It is harmless for the optimiser (the gradient along it is zero) but it makes parameter tables misleading. See the open decision below.

### Gradients

All closed form, in the same shape as `CMlpKern`:

- \(\partial k/\partial\theta\) for \(\sigma_w^2,\sigma_b^2,\sigma^2\) (and the per-dimension \(\sigma_{w,q}^2\) for ARD), through \(a,a',\cos\theta\).
- \(\partial k/\partial\mathbf x\) for `getGradX`, `getDiagGradX`.
- The \(\theta\to0\) and \(\theta\to\pi\) limits need explicit handling: \(J_1\) is smooth, but the derivative \(\partial J_1/\partial c=(\pi-\theta)\) is finite while \(\partial\theta/\partial c\) diverges. Write \(\partial k/\partial c\) through \(J_0=(\pi-\theta)\) directly, as `CArcCosineKern::getGradX` already does, and clamp \(c\) as `arccosClampCos` does.

The Phase 3 guard change is the main design point. Today the Python façade decides capability by comparing a name string with `"mlp"`. That is the "switch statement scattered across prediction, gradient, and I/O code" the compose-through-interfaces tenet warns about. We replace it with a virtual `CKern::supportsRidgeWindows()` (default `false`; `true` for MLP, MLP-ARD, ArcCosine, ReLU, ReLU-ARD, and compounds whose non-trivial part is one of these). The next dot-product kernel then costs no façade edits.

### Design decisions that need a ruling

1. **Parameterisation.** (a) Keep three parameters for symmetry with `mlp` and accept the flat direction above; (b) drop `variance` and fold the output scale into `weightVariance` and `biasVariance`; (c) keep three parameters and fix the flat direction by default via a transform or prior. *Recommendation:* (a) for Phase 0, because it keeps `getVariance()`, `setParam(variance, 2)` in `makeLayerKern`, the GPy-style `variance` handle and every generic loop unchanged. Document the degeneracy in the class comment and in `docs/`. Revisit if SCG shows slow progress along the flat direction in the deep GP gate.
2. **Class layout.** Two classes (`CReluKern`, `CReluardKern`, mirroring MLP / MLP-ARD) or one with an `order` parameter on the existing `CMlpKern`. *Recommendation:* two new classes. `CMlpKern` carries `asin`-specific weight-space code; an `order` flag would branch inside every hot function, which the performance tenet rejects.
3. **`mlp_init='scaled'`.** The mean-square-norm initialisation in [CIP-0041](./cip0041.md) targets the erf unit's saturation. For ReLU the analogue is a variance-preserving He-style initialisation (\(\sigma_w^2=2/d_\text{in}\)). *Recommendation:* defer; Phase 3 makes `mlp_init='scaled'` refuse `relu` with a typed error that names the option, and we revisit once there is a ReLU deep GP result to measure.
4. **Relation to `ArcCosine`.** Keep `ArcCosine` unchanged. Add a pinned test that `relu(1,1,1)` equals `arccos1` up to the stated constant. Do not alias them.

### Phase 4 — remaining surfaces

## Backward Compatibility

- New kernel types only. No existing parameter, stream field or CLI flag changes meaning.
- `.model` streams for `relu` / `reluard` start at version 1 with their own `type` string; existing `mlp` and `arccos` streams are untouched.
- Phase 3 replaces name checks with a capability query. Existing error messages for unsupported combinations (for example `inducing='weightspace'` with `rbf`) must keep their text where tests match on it; new messages name the kernel and the missing capability.

## Testing Strategy

Per the assert-and-verify tenet, no phase closes without a gradient check and a reference.

- **Independent oracle.** Monte Carlo covariance of a wide finite ReLU network (\(10^6\) hidden units, fixed seed) against the closed form, to a tolerance set by the Monte Carlo standard error. This guards the constant and the \(\Sigma\) algebra without relying on `CArcCosineKern`.
- **Cross-kernel pin.** `relu(1,1,1)` equals `arccos1` up to the documented constant.
- **Gradients.** Finite differences for `getGradParams`, `getGradX`, `getDiagGradX`, all ridge gradients and the deep GP objective, including points at \(\theta\approx0\) and \(\theta\approx\pi\) (duplicated inputs, antipodal inputs) where the limit handling matters.
- **Batched equals oracle.** `inducingGradX/Z` against the base-class loop at \(10^{-12}\).
- **Symmetry and PSD.** `K` symmetric, with a non-negative smallest eigenvalue up to round-off, on random inputs.
- **Round trip.** `.model` write/read/`equals` at `ndlutil::MATCHTOL`.
- **Build gate.** `make` and the test binaries (`testKern`, `testInducingGradZ`, `testDeepGp`, `testSvgp`, `testSviBayesGplvm`) pass on this machine; Python tests under `python/tests/` pass.
- **No MATLAB reference.** The existing `matfiles/` fixtures have no ReLU case. The Monte Carlo oracle and the GPy-free closed form stand in; we do not add a MATLAB dependency.
